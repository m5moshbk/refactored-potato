# M5mOsH AI Capability Registry — Schema Security v1.0

**Owner:** M5mOsH  
**Status:** Design and repository artifact; not deployed  
**Database target:** PostgreSQL 14+  
**Rights:** © M5mOsH All Rights Reserved

## 1. Scope and security boundary

This document describes the security controls expected for the registry schema. Committing this document and `schema.sql` does not create a database, execute a migration, install software, configure credentials, or connect to any external service.

The registry stores technology metadata, versions, capabilities, evidence references, evaluation outcomes, integration records, decisions, and audit events.

It must not store:
- API keys, passwords, OAuth access or refresh tokens, private keys, or session cookies.
- Customer personal data or unrelated confidential business records.
- Raw credentials embedded in URLs, logs, evidence notes, or JSON metadata.

Use references to an approved secret manager for any future integration credentials. Never copy secret values into this registry.

## 2. Data model and integrity controls

- `technologies.canonical_key` is the stable unique identifier chosen by the registry.
- `technology_versions` stores version history; do not overwrite an old version to represent a new release.
- Composite foreign keys on sources, evaluations, and capability evidence prevent records from accidentally referencing a version, source, or capability belonging to another technology.
- `ON DELETE RESTRICT` is intentional. The registry preserves provenance; removal should normally be represented by a lifecycle or support status rather than cascading deletion.
- JSONB is limited to flexible metadata and structured test evidence. Core relationships and statuses remain relational and constrained.
- UUID values are generated by the application or a separately reviewed database default policy.

## 3. Lifecycle state machine

Allowed lifecycle transitions:

| Current state | Allowed next state |
|---|---|
| discovered | verified, rejected, deprecated |
| verified | evaluated, rejected, deprecated |
| evaluated | approved, rejected, deprecated |
| approved | integrated, deprecated |
| integrated | deprecated |
| rejected | terminal |
| deprecated | terminal |

A same-state update is permitted. Reopening a rejected or deprecated technology requires a separately reviewed administrative process; do not bypass the transition trigger.

### Approval gate

Before changing a technology to `approved`, the database trigger requires:

1. At least one source with `verification_status = 'verified'`.
2. At least one version with `support_status = 'active'` and a non-null `verified_at`.
3. At least one evaluation with `test_status = 'passed'`, `critical_findings_count = 0`, and a non-null `tested_at`.
4. An explicit `decisions` row with `decision = 'approve'`.

The approval decision must be inserted before the lifecycle update, within the same transaction. The caller must ensure the decision references the correct human approval record; a non-empty text reference alone is not proof of authorization.

The schema does not assign automatic scores or decide whether a technology is safe. Reviewers must assess the actual evidence, evaluation scope, license, privacy, cost, operational fit, and unresolved risks.

## 4. Database roles and least privilege

Create roles through a separately reviewed deployment procedure. Do not embed passwords in SQL files or commit them to Git.

Recommended role separation:

| Role | Expected access |
|---|---|
| Registry owner / migration role | Owns schema and performs reviewed migrations; credentials held outside the repository |
| Registry application writer | SELECT/INSERT/UPDATE only on explicitly required operational tables; no schema ownership |
| Registry auditor | SELECT on approved registry tables and audit events |
| Registry ingestion worker | Narrow INSERT/SELECT scope for approved ingestion workflow |
| Registry read-only client | SELECT only on approved views/tables |

Additional requirements:
- Revoke unnecessary privileges from `PUBLIC`.
- Do not grant the application role ownership of tables, triggers, or schemas.
- Do not grant application roles `TRUNCATE`, `ALTER`, `DROP`, or unrestricted delete permissions.
- Grant writes table-by-table and operation-by-operation.
- Use row-level security if multiple tenants or security domains are introduced; define and test tenant identity propagation before enabling it.
- Keep production and test credentials separate.
- Rotate credentials through the approved secret-management process.
- Log privileged access and review role membership periodically.

## 5. Audit event integrity

The base schema installs a row-level trigger that rejects UPDATE and DELETE operations on `audit_events`; Phase B adds a statement-level trigger that rejects TRUNCATE. These are database guardrails, not cryptographic immutability.

Important limitations:
- A database superuser, table owner, or sufficiently privileged administrator may disable triggers or alter the table.
- The triggers do not prove that an event is truthful or complete.
- The triggers do not automatically create audit events for changes to other tables.

Required operational controls:
1. Application code writes the business change and its audit event in the same database transaction.
2. The application database role receives INSERT and SELECT on `audit_events`, but not UPDATE, DELETE, TRUNCATE, or ownership. The trigger is defense in depth; privilege revocation remains mandatory.
3. Audit exports or backups are stored under separately controlled retention and access policies.
4. Administrative changes to schema, triggers, roles, and audit retention are logged outside the application database where feasible.
5. Audit event payloads must exclude secrets and unnecessary personal data.

## 6. Evidence provenance

- Prefer primary sources: official documentation, official repositories, release notes, license texts, and security advisories.
- Record the source URL, source type, verification status, checked date, and concise evidence notes.
- Distinguish verified facts from vendor claims, community reports, estimates, and unverified assumptions.
- Attach evidence to the specific capability it supports using `capability_evidence`.
- Record contradictory evidence rather than silently discarding it.
- Re-check sources when versions change or when an adoption decision is revisited.
- Do not infer that a source is authoritative merely because its URL is stored.

## 7. Evaluation requirements

A meaningful evaluation should identify:
- Exact technology and version tested.
- Test date, environment, configuration, and method.
- Functional outcomes and reproducible evidence.
- Security and privacy findings.
- License and usage restrictions.
- Cost model and resource requirements.
- Limitations, failure modes, and unresolved questions.

Scores are optional summary fields, not substitutes for evidence. Do not compare scores from different methods or environments as if they were directly equivalent.

## 8. Integration approval

An integration record in this registry is a record of status, not an authorization token.

New integration records must start in `proposed`. Allowed status transitions are:

| Current state | Allowed next state |
|---|---|
| proposed | approved, blocked, rejected |
| approved | in_progress, blocked, rejected |
| in_progress | integrated, blocked |
| blocked | proposed, in_progress, rejected |
| integrated | removed |
| rejected | terminal |
| removed | terminal |

The database trigger enforces these transitions, but an `approved` status is not permission to access an external system. A separate, explicit authorization for the exact integration action is still required.

Before any real integration:
1. Define exact target system, data flows, permissions, and rollback plan.
2. Review privacy, security, licensing, and operational impact.
3. Obtain explicit approval for that specific external change.
4. Use least-privilege credentials and a non-production test environment first.
5. Record implementation evidence and verification results.
6. Do not mark an integration as complete until the deployed behavior has been independently verified.

No production deployment, database migration, account change, secret creation, or repository merge is authorized by this schema commit.

## 9. Pre-deployment validation checklist

- [ ] Confirm PostgreSQL version and supported extensions.
- [ ] Review all DDL and trigger behavior.
- [ ] Test valid and invalid lifecycle transitions.
- [ ] Test approval gate with missing source, version, evaluation, or decision.
- [ ] Test cross-technology composite foreign-key rejection.
- [ ] Test audit UPDATE, DELETE, and TRUNCATE rejection using the application role.
- [ ] Verify application role cannot disable triggers or alter schema.
- [ ] Verify no role can read secrets because none are stored here.
- [ ] Test transaction rollback when audit insertion fails.
- [ ] Review query plans and index usefulness with representative data.
- [ ] Test backup, restore, retention, and disaster-recovery procedures.
- [ ] Complete a separate security review before production use.

## 10. Known limitations and follow-up design work

- The append-only UPDATE/DELETE/TRUNCATE triggers are not tamper-proof against privileged database administrators, who may disable triggers or alter the table.
- Audit events are not automatically generated for all table changes; application transaction discipline or separately reviewed audit triggers are required.
- The lifecycle and approval triggers do not replace human review or an external approval workflow.
- The schema does not yet implement tenant isolation, soft-delete policy, data-retention automation, signed evidence, or cryptographic audit chaining.
- URL syntax and safe URL schemes should be validated by the ingestion/application layer.
- `updated_at` fields require application updates or a separately reviewed trigger.
- Role grants and ownership are intentionally not included in this schema artifact because they depend on the actual deployment environment.

## 11. Change control

Any schema modification must:
1. Be proposed in an isolated branch.
2. Include a migration or clear schema diff.
3. Include tests for constraints, triggers, and backward compatibility.
4. Receive explicit approval before external writes.
5. Be reviewed before merge or deployment.
